# govengers/telemetry: design

Decisions are numbered `T<n>`; a later change gets a new number, never a rewrite. v0.1.0 (registry, metrics server, Gin RED middleware, tracing) predates this file; its reasoning is in the README and the standards rules MET and TRC.

## Health probes and pool metrics (15.11.2026)

| ID | Decision |
|----|----------|
| T1 | `health` is its own package on the standard library only, with `http.Handler`s (`LivenessHandler`, `ReadinessHandler`), so a `net/http` service, a Gin service and a headless worker with a tiny HTTP server all use it. `ginadapter.RegisterHealthRoutes` is the Gin helper; it takes `*gin.Engine`, not a router group, so the routes are always exactly `health.LivenessRoute` (`/api/health`) and `health.ReadinessRoute` (`/api/ready`), the constants the skip lists of metrics, wide events and traces use. |
| T2 | Liveness checks nothing and stays 200 while draining. A dependency in liveness turns a database outage into restarts of every pod; draining is readiness' job. |
| T3 | Checks are a `map[string]Check` in the options (DES-001), not a `Register` method: every check exists before the server starts, and a probe object that can change after the server serves is state nobody needs. A check is `func(ctx) error`, so `pool.Ping` fits directly. |
| T4 | One evaluation runs every check concurrently under one `Timeout` (default 1 s). The evaluator waits for the timer, not for the checks: a check that ignores its context is reported `timeout` on time, its goroutine runs on until it returns. A panicking check is recovered in its goroutine (CON-001) and reported `failed`. |
| T5 | Results are cached for `CacheFor` (default 1 s) and concurrent probes wait for the one running evaluation instead of starting their own. The readiness route is unauthenticated on the public port; without this, every request to it would ping the database. The evaluation runs on `context.WithoutCancel` of the first probe's context, so a probe that hangs up does not cancel the evaluation others wait for; waiters are bounded by the timeout. The cache clock is an unexported `now` field (TST-005). |
| T6 | `SetDraining` is one-way and short-circuits readiness to 503 `draining` without running checks. No `SetReady` toggle, no built-in pause: the pause before `Shutdown` belongs to main's drain, which owns the grace-period budget (LAY-003). |
| T7 | The readiness body is JSON with the overall status and a status per check (`ok`, `failed`, `timeout`), never the error text: the route is public and errors carry hostnames and addresses. The error goes to `OnCheckFailure`, called once per evaluation. It is a callback, not an `Observer` interface with Prometheus and OpenTelemetry adapters (LIB-012): the one consumer need is "log why the pod is unready", and an interface can be added later without breaking the callback. |
| T8 | Pool metrics live in `pgxadapter`, which does not import pgx. It reads the pool through `pgxadapter.Stat`, an interface with the nine methods of `*pgxpool.Stat` it needs, and main passes `func() pgxadapter.Stat { return pool.Stat() }`. The WP asked to keep pgx out of the root module; a nested module would have done that at the price of its own go.mod, tags, dependabot entry and justfile loops, while the interface needs none of it. A pgx release that changes a signature fails main's one-line closure at compile time. Verified against pgx v5.12.0; `EmptyAcquireWaitTime` needs v5.7.3 or newer. |
| T9 | The collector is a `prometheus.Collector` that reads one `Stat()` snapshot per scrape (MET-006), registered by `NewPoolCollector` on the caller's `Registerer` with the error returned (LIB-011). Names under subsystem `db_pool`: `connections{state}` (acquired, idle, constructing; one gauge with a state label, so the sum is the pool's size), `max_connections`, `acquires_total`, `acquire_duration_seconds_total`, `acquire_waits_total`, `acquire_wait_duration_seconds_total`, `canceled_acquires_total`. Cumulative durations are `_seconds_total` counters like `process_cpu_seconds_total`. Connection churn (`NewConnsCount`, the destroy counts) is left out until a dashboard needs it. One pool per namespace: a second pool under the same namespace is an `AlreadyRegisteredError`; a `pool` label can be added when a service needs two. |
| T10 | Review round 1 of the first PR, before release. `DefaultTimeout` is 800 ms instead of the 1 s of T4, below the Kubernetes default `timeoutSeconds` of 1, so the kubelet receives the 503 body. A check whose earlier run has not returned is reported `timeout` without being started again (a per-check flag), so a check that ignores its context costs one stuck goroutine, not one per evaluation. `OnCheckFailure` runs after the evaluation is published and its waiters are released, so a panic in it cannot leave later probes waiting forever; the price is that two evaluations can call it at the same time, which the doc states. The per-check flag clears in the deferred function of the check's run, so a check that ends through `runtime.Goexit` is started again. Readiness rechecks the draining flag after the evaluation, so a probe that started before `SetDraining` answers 503 too. |

## Database work on the wide event (16.11.2026)

| ID | Decision |
|----|----------|
| T11 | (supersedes the "no pgx import" part of T8) `pgxadapter` is the nested module `github.com/govengers/telemetry/pgxadapter`. The tracer of T13 implements pgx interfaces whose methods take `*pgx.Conn` and pgx's trace data types, so no structural interface avoids the import, and the work package asked to keep the root module free of pgx. A subpackage in the root module would have kept pgx out of a consumer's build through module graph pruning (the jobs J52 argument), but not out of telemetry's `go.mod`. The price: the justfile lints, tests (with its own coverage gate) and scans the module in a loop, dependabot watches its `go.mod`, and it is tagged `pgxadapter/vX.Y.Z`. The module does not require the telemetry module (its example builds a plain `prometheus.NewRegistry`), so it needs no `replace` and no lockstep release. The pool collector moved with it unchanged; `Stat` stays an interface because it lets the collector be tested without a database. pgxadapter was never in a tagged telemetry version (v0.1.1 predates it), so the move breaks no consumer and no import path is ambiguous. |
| T12 | (supersedes T9's one pool per namespace) `PoolOptions.Name` is required and becomes the constant label `pool` on every pool metric, so a service registers one collector per pool under one namespace. Required rather than defaulted: a default would let a second pool collide silently with the first in a dashboard query that does not filter, and one name in main costs nothing. The same `Namespace` and `Name` twice is still an `AlreadyRegisteredError`. |
| T13 | `pgxadapter.NewTracer()` returns a `pgx.QueryTracer`, `BatchTracer` and `CopyFromTracer` that writes, per unit of work, onto `wideevent.FromContext(ctx)`: `db.queries`, `db.duration_ms` (the sum), `db.slowest_ms` (the longest single call), and for the first failed statement `db.failure` (`canceled`, `timeout`, `connection`, `server`, `client`) and `db.sqlstate`. Key names follow the `db` namespace of standards LOG-004 (`queries`, `duration_ms`). The first failure, not the last: after a failure inside a transaction the following statements fail with `25P02`, which hides the cause. No SQL text, arguments or error text: a unique violation's Detail names the duplicate key. A server `57014` (query canceled) while the statement's context has ended is the context's `canceled` or `timeout`, otherwise `server`. A batch counts each statement and is timed once from `SendBatch` to `Close`, because pgx gives no per-statement time that excludes the application reading earlier results; pgx v5.12.0 calls `TraceBatchEnd` twice for a batch that fails early (in `SendBatch` and again in `Close`), so each call's time is added on its first end only; `PrepareTracer` is not implemented, since the implicit prepare of the statement cache already runs inside the query's time and an explicit `Prepare` is rare. No options: nothing is configurable, composition with otelpgx is pgx's `multitracer`, and a later setting would come as a second constructor, like the jobs `oteladapter.NewPropagator()`. The tracer writes the wide event directly instead of reporting through an `Observer` (LIB-012, a should): it is the pgx-to-wide-event adapter itself, and statement metrics in Prometheus are not asked for; the pool metrics cover saturation. |
| T14 | The running totals of an event live in the Tracer, in a `sync.Map` keyed by `weak.Pointer[wideevent.Event]`; `runtime.AddCleanup` on the event deletes the entry after the event is collected. The event has no read accessor for a field and no hook at its end, so the alternatives were a middleware per unit-of-work kind that puts an accumulator into the context (one more thing to wire in every HTTP, job and consumer entry point, and forgetting it records nothing) or a field read via `Fields()` on every statement (a copy of all fields and a lost-update race between concurrent statements). Each unit's mutex is held while its totals are written, so concurrent statements never write totals out of order. Memory is bounded by the live events plus one GC cycle. A statement without an event in its context costs one context lookup. |
| T15 | The trace ID key stays `tracing.KeyTraceID = "trace.id"` in this module for now. `wideevent.KeyTraceID` exists only on wide-event-logger's unreleased main; the released v1.0.0 that telemetry requires has no such constant, and the program's rules forbid requiring an unreleased version. Once wide-event-logger releases it, `tracing.KeyTraceID` becomes an alias of `wideevent.KeyTraceID`. A local probe (not committed) showed that requiring wide-event-logger's main, whose `go.mod` now requires pgx and embedded-postgres for its `postgresadapter`, adds neither to telemetry's `go.mod` or `go.sum`. `KeySpanID` has no counterpart in wide-event-logger and stays here. |
